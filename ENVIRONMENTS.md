# Environments

Three environments, each with **its own database and its own secrets**. Nothing
is shared — a QA session token is worthless in production, and seeding QA can
never touch live orders.

| | APP_ENV | API | Storefront | Admin | Database |
| --- | --- | --- | --- | --- | --- |
| Local | `local` | :5000 | :3000 | :3001 | `attume` |
| QA | `qa` | :5001 | :3100 | :3101 | `attume_qa` |
| Production | `production` | host URL | host URL | host URL | `attume_prod` |

Outside production every page shows a corner ribbon naming the environment, so
a QA tab is never mistaken for the live shop.

## How configuration is chosen

The API loads `.env.$APP_ENV` first, then falls back to `.env` for anything it
did not set. On a deployed host neither file exists and the platform's own
environment variables are used, which is why the same image runs everywhere.

Both Next apps read `.env.local` by default; the `:qa` scripts pass `.env.qa`
explicitly with `env-cmd`.

**Never commit a real env file.** Only `.env.example` is tracked; `.gitignore`
excludes `.env` and `.env.*` in every package.

## Running locally

```bash
docker compose up -d mongo          # one Mongo server, both databases live in it

cd backend  && npm run dev          # :5000 against attume
cd frontend && npm run dev          # :3000
cd admin    && npm run dev          # :3001
```

## Running the QA stack

```bash
cd backend  && npm run dev:qa       # :5001 against attume_qa
cd frontend && npm run dev:qa       # :3100
cd admin    && npm run dev:qa       # :3101
```

Seed it once — QA starts with an empty database:

```bash
cd backend
npm run seed:qa                                  # catalogue + demo orders
npm run create-admin:qa -- --email admin@attume.in --password 'choose one'
```

## Safety rails

- `assertNotProduction()` makes the seed scripts exit if `APP_ENV=production`.
  Demo orders can never be written into live data.
- `create-admin` has no such guard on purpose — creating the first production
  admin is a legitimate operation.
- Admin JWT secrets are separate from storefront secrets *and* separate per
  environment. Four distinct secrets per environment, twelve in total.
- Cookies must be `COOKIE_SECURE=true` and `COOKIE_SAMESITE=none` anywhere the
  API and the site sit on different HTTPS domains.

## Deploying

`backend/render.yaml` describes both API services: the `qa` branch deploys the
QA API, `main` deploys production. Secrets marked `sync: false` are entered in
the dashboard; JWT secrets are generated by Render so nobody ever sees them.

The two Next apps deploy to Vercel as separate projects with the root directory
set to `frontend` and `admin`. Each project needs `NEXT_PUBLIC_APP_ENV` and
`NEXT_PUBLIC_API_URL` pointing at the matching API, and the API's `CORS_ORIGINS`
must list those deployed origins or the browser will refuse every request.

Databases: MongoDB Atlas, one cluster, separate databases per environment.

## Branches

```
main  → production
qa    → QA
```

Work on a feature branch, merge to `qa`, verify on the QA stack, then merge to
`main`.

## Commerce settings per environment

`FREE_SHIPPING_THRESHOLD`, `SHIPPING_FEE`, `COD_ENABLED` and
`COD_MIN_ORDER_VALUE` are environment variables, so QA can exercise edge cases
(free shipping at ₹1, COD disabled) without touching production behaviour.
Current defaults: free shipping above ₹2000, ₹99 otherwise, COD enabled above
₹999.
